# WakeIntent 需求分析

> 文档状态：Draft 0.1  
> 更新日期：2026-09-01  
> 适用范围：WakeIntent v0.1 概念验证阶段

## 1. 项目背景

当前多数对话式 AI 采用请求—响应模式：用户发起消息，AI 才开始工作。定时提醒能够在未来触发消息，但通常要求用户明确创建任务；heartbeat 能让 Agent 周期性醒来，却可能产生无意义模型调用，并且容易在上下文已经变化后继续发送过时的跟进消息。

WakeIntent 关注一个更窄的问题：

> 对话中出现了一个未来可能值得再次联系用户的机会时，系统如何把它表示为可跨时间存在、可重新验证、可取消和可过期的 `ContactIntent`，并在真正联系前决定联系、推迟、取消、过期或保持沉默。

项目不试图发明新的大模型，也不在 v0.1 构建完整 Agent、消息平台或 AI 伴侣。v0.1 只验证 `ContactIntent` 是否是一个独立、可复用且优于“记忆 + heartbeat”的领域抽象。

## 2. 核心假设

### H1：独立建模假设

将未来跟进机会建模为带来源证据、时间窗口、失效条件和打扰成本的 `ContactIntent`，能够表达普通长期记忆和定时任务难以完整表达的语义。

### H2：重验证价值假设

在联系前读取最新上下文进行重验证，能够减少已解决、已取消、已过期或不再适合联系的话题被错误触达。

### H3：沉默价值假设

把 `silent` 作为一等决策结果，而不是生成失败，能够降低无理由误触达率和重复联系率。

### H4：框架无关假设

同一套 `ContactIntent` 契约和决策接口可以被不同 Agent 框架、模型供应商、业务策略和客户端复用。

## 3. 目标用户与利益相关者

### 3.1 v0.1 主要用户：对话式 AI 开发者

他们希望为现有聊天机器人、AI 助手、教育产品、客服、游戏 NPC 或 AI 伴侣增加主动跟进能力，但不想自行处理话题失效、取消、过期、打扰治理和评测。

### 3.2 次要用户：研究者与开源贡献者

他们需要一套可重复运行的场景、基线和决策日志，用于研究什么时候应该主动联系以及什么时候应该保持沉默。

### 3.3 后续用户：最终使用者

最终用户通过参考客户端或第三方集成体验主动联系能力。角色、免打扰设置和可解释记录属于后续阶段，不是 v0.1 的交付中心。

## 4. 典型使用场景

### UC-01 正常跟进

用户说：“周五应该能收到面试结果。”系统提取候选意图，在合理时间窗口内重验证；如果没有新信息且策略允许，输出 `contact`。

### UC-02 提前解决

用户在到期前说：“拿到 offer 了。”系统识别原意图已经解决，输出 `resolve`，不得再次询问结果。

### UC-03 显式取消

用户说：“不用再问这件事。”系统输出 `cancel`，后续相似评估不得重新触达该意图。

### UC-04 自然过期

意图超过有效期且没有新的有效证据，系统输出 `expire`。

### UC-05 暂不打扰

用户最近明确表示忙碌、开启免打扰或连续未回应，系统输出 `defer` 或 `silent`。

### UC-06 多意图竞争

多个意图同时进入可评估窗口，系统根据重要程度、打扰成本和预算决定少量最值得联系的意图，其余推迟或保持沉默。

### UC-07 负例

用户只是描述一般事实或已经结束的话题，不应创建未来联系意图。

## 5. v0.1 功能需求

| ID | 需求 | 优先级 |
|---|---|---|
| FR-001 | 接受框架无关的对话事件输入 | Must |
| FR-002 | 通过 `extract()` 从对话中返回零个或多个候选 `ContactIntent` | Must |
| FR-003 | 每个候选意图必须绑定可追溯的来源证据 | Must |
| FR-004 | 使用 JSON Schema 定义并校验 `ContactIntent` | Must |
| FR-005 | 支持候选意图的持久化序列化与恢复 | Must |
| FR-006 | 通过 `reevaluate()` 接受意图、最新上下文、当前时间、用户状态和策略 | Must |
| FR-007 | 重验证返回 `contact`、`defer`、`cancel`、`expire`、`silent` 或 `resolve` | Must |
| FR-008 | 决策结果必须包含理由、引用证据、置信度和可选的下次评估时间 | Must |
| FR-009 | 在模型判断前执行确定性的过期、显式取消、免打扰和预算门控 | Must |
| FR-010 | 保存追加式决策事件日志，不覆盖历史理由 | Must |
| FR-011 | 提供 fake clock 驱动的生命周期测试 | Must |
| FR-012 | 提供“记忆 + heartbeat”基线，使用相同模型、上下文和时间信息 | Must |
| FR-013 | 生成机器可读和人可读的评测报告 | Should |
| FR-014 | 提供模型适配接口和至少一个 OpenAI-compatible 参考适配器 | Should |
| FR-015 | 提供最小 CLI，用于运行场景、基线和评测 | Should |

## 6. 非功能需求

| ID | 需求 | 验收方向 |
|---|---|---|
| NFR-001 可移植性 | 核心领域模型不得依赖具体 Agent、数据库或 UI | Core 可单独导入并运行 |
| NFR-002 可序列化 | 输入、意图、决策和事件均可表示为 JSON | 通过 JSON Schema 校验 |
| NFR-003 可追溯 | 每次提取与重验证必须能回指输入证据 | 报告展示 evidence refs |
| NFR-004 可测试 | 时间、模型和存储均可替换 | fake clock 与 fake model 测试 |
| NFR-005 可复现 | 评测记录模型、版本、参数、场景版本和运行时间 | 输出 run manifest |
| NFR-006 隐私 | Core 不默认上传或记录完整敏感对话 | 日志支持脱敏和最小化 |
| NFR-007 安全默认 | 用户授权、显式取消、免打扰和过期规则优先于模型 | 确定性门控测试 |
| NFR-008 成本可见 | 记录模型调用次数、输入输出 token 和估算费用 | 评测报告包含成本字段 |
| NFR-009 向后兼容 | Schema 包含版本字段，破坏性修改有迁移策略 | fixture 覆盖旧版本 |

## 7. v0.1 明确不做

- 不实现真实短信、邮件、Telegram、Discord 等渠道投递。
- 不宣称 `contact` 等于用户已经收到消息。
- 不实现常驻 heartbeat、cron 平台或通用任务调度器。
- 不实现 lease、分布式锁、并发投递和 delivery receipt。
- 不实现完整长期记忆、向量数据库或 RAG 平台。
- 不实现角色 UI、桌面客户端、移动端和完整聊天产品。
- 不实现 Agent 工具调用、自动操作电脑或多 Agent 编排。
- 不以生成文案是否“像真人”作为首要评测目标。

## 8. 业务规则

1. 用户显式取消拥有最高优先级，模型不得覆盖。
2. 已过期意图不得输出 `contact`。
3. `contact` 是一次决策事件，不是投递成功状态。
4. `silent` 表示本次评估不联系，不自动终结意图。
5. `resolve` 表示最新上下文证明目标事项已经得到结果。
6. 所有模型决策必须保留证据和解释，但解释不能替代确定性规则。
7. 低置信度候选保持 `candidate`，不得自动升级为可联系意图。

## 9. 成立与失败标准

### 项目成立的最低证据

在相同模型、对话、上下文窗口和时间信息下，WakeIntent 相比“记忆 + heartbeat”基线：

- 更准确地识别提前解决、显式取消和自然过期；
- 显著降低无理由误触达和重复联系；
- 在应该沉默的场景中保持更高准确率；
- 决策解释与实际状态变化保持一致；
- 额外复杂度和模型成本处于可接受范围。

### 可证伪条件

如果 WakeIntent 无法稳定优于基线，或者优势只能依赖特定 Prompt、特定客户端或人为挑选的少量 Demo，则应将它降级定位为聊天应用功能，而不是独立引擎。

## 10. 待确认事项

- 首个真实模型适配器选用哪一家供应商，仅作为参考实现，不进入 Core。
- v0.1 公开场景集的规模与人工标注流程。
- 联系意图是否需要 `subject` 与 `target` 分离，以支持群聊和多参与者。
- 敏感领域是否在 v0.1 直接禁止，还是通过策略标注为永不自动联系。
- 项目许可证和贡献者协议。
