# 第一阶段可行性结论

> **历史文件：本页的 GO 结论已被 2026-09-05 的最终冻结对照实验取代。**
> 第一阶段只证明机制可以运行；20 个场景 × 3 轮的强 Baseline 对照没有发现足以抵消复杂度与 Token 成本的用户可见优势。当前停止将 WakeIntent 作为独立产品扩张。详见[正式实验报告](../reports/intent-continuity-value/2026-09-05T11-50-41.477Z/experiment-report.md)。


> 结论：**GO——可以作为研究型 Alpha 项目正式启动**  
> 结论日期：2026-09-02  
> 结论强度：证明独立机制值得继续验证；尚未证明产品或成本优势

## 1. 我们实际验证的问题

第一阶段没有尝试证明“AI 会主动发消息”是新发明，而是验证一个更窄的假设：

> 正常对话能否产生一个跨时间存在的 `ContactIntent`；当新对话改变其理由时，系统能否只唤醒相关意图，重新判断或直接闭合，并取消未来调度，而不是等固定 heartbeat 到来后才处理。

这个假设已经通过工程实现和真实模型时间线得到正面结果。

## 2. 为什么判定 GO

### 2.1 机制能够工作

当前实现已经具备框架无关的结构化意图、生命周期、确定性硬门控、最新上下文重验证、选择性 relevance routing、审计记录、可恢复调度语义和强 baseline 对照。完整构建、类型检查和 73 项自动测试通过。

### 2.2 它与固定 heartbeat 有实质差异

朴素 heartbeat 在无事发生时仍周期性调用模型；WakeIntent 在没有候选意图时不创建调度，在无关事件到来时不唤醒语义决策，在意图提前失效时删除未来调度。因此系统可以长期休眠，只由宿主的对话事件和最小时间唤醒触发，不需要模型常驻思考。

### 2.3 它与强 due-gated heartbeat 也存在一个较窄但真实的差异

强 baseline 在到期时读取最新上下文，同样能避免很多错误消息，所以不能故意把它说弱。WakeIntent 的差异是把失效条件提前保存在意图中，并允许新上下文立即关闭状态。

在最终间接失效时间线中：

- WakeIntent 与 baseline 的最终行为都正确；
- WakeIntent 提前 26 小时关闭失效意图；
- WakeIntent 使用 2 次模型调用，baseline 使用 3 次；
- WakeIntent 使用 2854 Token，baseline 使用 2280 Token。

这证明额外结构可以减少一次未来模型判断，但当前结构化语义仍有约 25% Token 溢价。它是一个可继续优化的工程权衡，而不是已经全面胜出的结果。

### 2.4 关键路由瓶颈已有可行解

只返回匹配意图的 `0.1.1` 路由协议在 14 个开发场景中，混合路由单轮 14/14，使用 7 次模型调用和 6428 Token；全模型路由同样 14/14，但使用 14 次调用和 12610 Token。三轮混合路由共 42 次预测，在一次透明记录的时间窗口标签修订后为 42/42，预测集合三轮一致。

增加影响类型后的 `0.2.0` 协议完整运行一次仍为 14/14；但随后单独复验临时全局免打扰时，模型漏掉一个同样在免打扰窗口内到期的 intent，recall 为 0.5。已选项保守输出 `reevaluate`，没有误终止。这个结果说明安全的本地规则加模型回退可以避免“每条新消息都调用模型”，但路由并不稳定 100%，旧三轮结果也不能替代新协议的重复评测。

该失败还明确了组件边界：全局“别主动联系我”应进入 `ContactPolicyState` 并由硬门控广播，而不是交给逐 intent relevance router。自然语言全局策略入口是 Alpha 的首个必做缺口。

截至 2026-09-02，第三小步已经完成：除 `ContactPolicySignal`、`ContactPolicySnapshot`、确定性 reducer、公共 JSON Schema 和自然语言参考适配器外，连续时间线已经消费正式策略信号。模型输出必须经过用户证据、时间边界和信号字段一致性校验，不能直接修改策略；一条有限免打扰可确定性地重排多个意图，绕过逐意图路由，并避免原到期点的语义模型调用，提前恢复后还能还原原排期。当前 95 项离线测试通过；这证明抽象已经产生可观测的编排收益，但尚未证明真实模型的策略提取 precision/recall。下一步是冻结策略正负例并进行真实模型评测。

第四小步给出了第一批真实模型证据。原始冻结集 20 条达到 18/20，signal precision/recall 均为 0.90，所有 11 个负例通过；这支持“明确全局策略与普通忙碌、单意图取消可以分离”的核心边界。失败分析促使提取输入加入当前策略快照，而不是用 Prompt 强行猜测恢复语义。状态感知版本新增的 8 条未见 holdout 全部通过，precision/recall 均为 1.0；28 条全量运行有一条因复合状态的序列化形状被本地拒绝，安全归一化后定向复验通过。原始报告全部保留，不能将定向复验改写成全量 100%。当前 101 项离线测试通过。

因此项目已从“值得验证的抽象”前进到“有初步真实数据支持的 Alpha”：高风险负例没有误升格为全局禁用，当前策略状态确实解决了恢复语义歧义，时间线广播确实减少逐意图无意义唤醒。它仍未达到产品价值证明，因为样本规模小、只运行一轮，尚未完成端到端强 baseline 对照和真人打扰感评测。下一步应重复冻结集评估稳定性，并加入含全局策略变化的连续时间线基线对比。

随后对 8 条状态 holdout 重复三轮，真实结果为 23/24、precision 1.0、0 个误报；7/8 场景三轮完全稳定。唯一波动来自混合 JSON Schema 的无关 nullable 字段，而非全局策略与普通语义混淆。`0.3.0` 已把三种策略操作拆为独立数组并通过 101 项离线测试。

对同一个合成复合恢复场景进行的三次 `0.3.0` 定向冒烟报告为 `reports/policy-signal-runs/2026-09-02T04-51-09.282Z.json`：3/3 精确通过，0 个错误，三轮均包含 `clear-do-not-disturb` 和 `set-authorization=granted`，稳定性为 1/1；总计 2331 Token，费用为 `null`。这验证了新 Structured Outputs 协议已消除已知复合恢复形状失败，但不能表述为全部策略场景的 100% 验证。

P1 已新增一个含两个意图的全局免打扰离线连续时间线，并将 fixture、两套 oracle、评分器与报告脚本接成可重复实验。离线报告 `reports/policy-longitudinal-offline/2026-09-02T06-28-49.066Z.json` 中，两套系统最终都正确联系两个事项；WakeIntent 在原排期 0 次唤醒并立即吸收全局策略，强 baseline 在 52 小时后的原排期用一次公平批处理读取最新上下文。与此同时，WakeIntent 的逻辑阶段调用上限是 5，baseline 是 3；这进一步限定了当前价值主张是“更早的共享状态治理”，而不是“总体调用更少”。尚未运行新的真实端到端 API 对比。

## 3. 目前不能说什么

项目现在不能宣称：

- “比成熟 proactive agent 更先进”；
- “整体比 heartbeat 更省 Token 或费用”；
- “已经解决误打扰”；
- “路由准确率是 100%”；
- “已经是生产可用引擎”。

正确表述应是：

> WakeIntent 是一个正在验证的、框架无关的对话联系意图生命周期引擎。早期实验表明，它可以在不持续运行模型的情况下，从对话建立未来联系意图，并在相关新上下文出现时选择性取消、完成或重评；在一个间接失效时间线中，它比强 due-gated baseline 少一次模型调用并提前清理状态，但总体 Token 优势和真实用户价值仍需冻结评测证明。

## 4. Alpha 阶段的生死指标

下一阶段不是先做 UI、角色扮演或多渠道，而是冻结评测并尝试推翻项目。建议门槛：

- 不少于 40 个从开发集隔离的时间线，包含至少 15 个无关或诱饵负例；
- relevance route precision 不低于 0.95，recall 不低于 0.85；
- 自动 `cancel` / `resolve` 的误终止率不高于 1%，否则只能降级为 `reevaluate`；
- 全局授权、免打扰和预算变化先进入策略层并广播，禁止依赖逐意图路由完整召回；
- 重复联系率为 0，显式取消后的再次联系率为 0；
- 与强 baseline 使用相同模型、原始对话、时间信息和批处理机会；
- 分别公布模型调用、输入 Token、输出 Token、费用、误触达和状态陈旧时长；
- 至少三轮重复，并由不知道系统来源的人复核含糊标签。

若 WakeIntent 只能更早改变内部状态，却不能降低任何误触达、下游错误、调用成本或用户等待，它应收缩成现有 Agent 的一个可选生命周期组件，而不是宣传成独立平台。若它在低误终止率下持续减少过期判断、释放调度和预算，并让多个宿主框架复用同一协议，就有资格继续发展为独立开源引擎。

## 5. 立项决定

**可以启动项目，但启动的是“可证伪的研究型 Alpha”，不是已经验证成功的产品。**

第一阶段已经排除了“根本做不到”“只能常驻运行”“必然每条消息调用模型”“完全等同固定 cron”这几种否定；也发现了它暂时不比强 baseline 省 Token、用户可见收益仍不足的真实风险。这正是值得立项继续做的状态：有一个可运行、可测量、可能成立的独立机制，同时保留明确的失败条件。

为避免无限对比，最终可行性收口已经固定为 `evals/alpha-closure-longitudinal-v0.1.json` 的 12 条时间线。通过条件是至少 10/12、WakeIntent 误触达为 0，且所有安全类场景通过；满足后不再扩大立项实验，直接进入 API 稳定化、持久化和参考应用开发。运行前 runner、评分器、全局授权广播和强 baseline 累计上下文均已离线验证，当时 108 项测试通过。

用户曾授权一次真实收口，但运行在最终报告落盘前随网络/会话中断，旧 runner 没有中间 checkpoint，因此既不能恢复结果，也不能知道已经消耗的请求数。该轮只算一次基础设施事故，不参与 GO/REVIEW。runner 现已补上逐请求预算日志、逐场景 checkpoint、稳定幂等键和同轮恢复；下一步只缺一次重新明确授权的新轮次。无论新运行结果是否漂亮，都应按冻结停止规则给出 GO 或 REVIEW，而不是继续加题直到得到想要的答案。

## 6. 真实收口后的最终判断

新的获授权轮次已经完成。原始报告 `reports/alpha-closure-runs/2026-09-02T07-37-32.948Z.json` 为 12 条全部执行、8 条通过、2 条评分失败、2 条因 baseline 过量提取而无法评分；实际 60 次 HTTP 尝试、0 自动重试，已保存 47,642 Token，另有 4 次调用的 Token 因旧错误路径未保留。审计报告 `reports/alpha-closure-runs/2026-09-02T07-37-32.948Z.audited.json` 在不改变原始结果的前提下将缺失停止判定明确为 **REVIEW**。

**项目层面的决定是：有价值，停止可行性拉锯，进入有边界的 Alpha 开发；评测层面的决定是：尚未 GO，不能宣称已经优于 heartbeat。**

成立的差异化不是“AI 自己一直思考”，而是一个框架无关的未来联系生命周期：正常对话创建 `ContactIntent`，新对话事件可以在原到期前完成、取消或改变全局联系政策，到期后仍要结合最新状态决定联系或沉默。真实运行中，提前获知结果、显式取消、间接目标失效和全局撤销授权均通过；其中 WakeIntent 会在新上下文到达时立即清理状态，而强 baseline 到原到期点才处理。模糊未来愿望负例中 WakeIntent 返回 0 个候选，baseline 产生了 1 条 memory，也说明独立的 ContactIntent 提取契约具有实际意义。

尚未成立的是成本和用户可见优势。10 条可完整计账的场景中，WakeIntent 使用 34 次调用和 30,995 Token，baseline 使用 22 次调用和 16,647 Token；已评分场景两者误触达都为 0。WakeIntent 当前换来的是更早、更细的状态治理和审计，而不是更低成本。免打扰结束后的补发/过期语义也必须从模型自由判断上升为明确产品策略。

接下来不再新增大规模对比来证明项目“配不配存在”。Alpha 只处理三项已知问题：迟到联系策略、正确沉默的评测表达、错误路径完整保留与 baseline 过量提取评分。修完后直接进入持久化 API、框架适配器和最小参考应用；原始 REVIEW 报告继续公开保留，作为项目诚实性的证据。

收口基础设施修复后，4 个包构建、类型检查和 109 项离线测试全部通过。
