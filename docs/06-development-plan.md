# WakeIntent 开发计划

> 文档状态：Draft 0.1  
> 更新日期：2026-09-01  
> 原则：按可验证增量推进，不以功能数量衡量进度

## 1. 阶段总览

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| P0 立项 | 固定需求、领域边界和技术决策 | 文档完成评审，关键术语无冲突 |
| P1 契约 | 建立 Schema、状态机和事件模型 | 所有 fixture 可校验，状态测试通过 |
| P2 核心用例 | 实现 extract/reevaluate 与端口 | FakeModel 端到端场景通过 |
| P3 评测基线 | 建立场景格式、heartbeat 基线和指标 | 同一命令可运行两组并输出报告 |
| P4 真实模型 | 接入参考模型并运行冻结评测 | 产生可复现的首轮结果 |
| P5 公开验证 | 整理文档、示例和贡献入口 | 外部开发者能复现结果 |
| P6 产品化探索 | 决定投递、角色和参考客户端优先级 | 基于数据而不是想象立项 |

## 2. P0：立项与设计

### 交付物

- 需求分析；
- 领域模型；
- 系统架构；
- 技术选型；
- 评测与验收方案；
- 风险登记与开放问题。

### 退出条件

- `ContactIntent`、Decision、State 和 Delivery 的概念不混用；
- v0.1 非目标得到明确确认；
- 基线和公平性要求可执行；
- 不存在阻止 P1 的关键开放问题。

## 3. P1：Schema 与状态机

### 任务

- 建立 pnpm workspace 和严格 TypeScript 配置；
- 编写 ContactIntent、Decision、DomainEvent JSON Schema；
- 接入 Ajv 校验；
- 实现纯函数状态转移；
- 建立 Clock、Store、Model 端口；
- 编写非法状态、时间边界和序列化测试。

### 退出条件

- 合法与非法 fixture 均有覆盖；
- Core 可在无模型、无数据库、无网络环境下完成测试；
- 业务代码不直接读取系统时间。

## 4. P2：提取与重验证

### 任务

- 设计标准化 ConversationEvent；
- 实现 `extract()` 编排；
- 实现候选去重和最低证据规则；
- 实现确定性门控；
- 实现 `reevaluate()` 编排；
- 使用 FakeModel 覆盖所有决策分支；
- 生成追加式事件日志。

### 退出条件

- 八类核心场景在 FakeModel 下端到端通过；
- 显式取消和过期无法被模型覆盖；
- `contact` 不产生伪投递状态。

## 5. P3：评测与基线

### 任务

- 固定场景 Schema；
- 编写第一批开发场景；
- 实现“记忆 + heartbeat”基线；
- 实现指标和报告；
- 实现连续时间线运行器，验证提前终止后不会在原到期点重复唤醒；
- 同时维护朴素 heartbeat 与带 `dueAt` 过滤的强 baseline；
- 记录模型、Prompt、参数、token、费用和运行时间；
- 建立盲审输出格式。

### 退出条件

- 同一个命令可以对两组运行相同场景；
- 报告可追溯到每个原始决策；
- 公平性检查能在配置不一致时直接失败。
- 无关上下文不触发语义重验证，相关上下文能提前结束意图且移除后续调度。

## 6. P4：真实模型实验

### 任务

- 实现 OpenAI-compatible 参考适配器；
- 将开发场景扩充到可公开评测规模；
- 冻结测试集；
- 每个配置进行多次运行；
- 分析失败样本、成本和不确定性；
- 根据结果决定继续、调整定位或停止。

### 退出条件

- 结果可由另一台机器复现；
- 正面和负面结果均公开；
- 能回答 WakeIntent 是否稳定优于基线，而不是只展示案例。

## 7. P5：开源发布准备

P0–P4 完成后再统一编写或重构 README、Quick Start、API 文档和示例，确保宣传与真实能力一致。

发布前至少完成：

- 安装和运行路径；
- 版本化 Schema；
- 示例项目；
- 贡献指南；
- 安全与隐私说明；
- 许可证；
- Related Work 与诚实差异说明；
- 首份公开评测报告。

## 8. P6：后续功能的进入条件

### 可靠投递

只有出现真实渠道适配需求后，才设计 lease、attempt、receipt、retry 和幂等投递。

### 角色策略

只有 Core 已证明有效后，角色才作为 Policy 扩展进入；角色不得覆盖用户授权、免打扰和敏感规则。

### 参考客户端

只有明确需要展示真实交互、决策解释和设置管理时才选择 PWA、Tauri 或 Electron。

### Agent 适配器

优先选择能带来真实使用反馈的一个生态，而不是同时维护 OpenClaw、AstrBot、LangGraph 和 MCP。

## 9. 开发纪律

- 每个提交只解决一个可描述的问题；
- 先写状态和边界测试，再接真实模型；
- AI 生成的代码必须能由维护者解释；
- 不合并无法说明失败模式的抽象；
- 新依赖必须记录用途、替代方案和退出成本；
- 不为了展示“工程量”提前引入微服务或复杂基础设施；
- 发现核心假设不成立时允许停止或转为应用功能。
